# Person 1 mock handoff — version 0.1.0

Person 2 provides proposed profile and matching contracts, bounded fictional CV
intake, explicit transfer/preference explanations and top-N target pinning.
See [the current Person 2 handoff](PERSON_2_MATCHING_AND_CV_INTAKE.md) for functions, scoring,
review semantics, limits and changed response fields. These proposals still need
consumer review; HTTP routes and review UI remain Person 5's integration work.

This initial contract is ready for teammates to consume and review. All data is
synthetic, including role requirements, tasks and importance weights. It is for
integration, not evidence of actual hiring requirements or market demand.
Coordinate skill IDs with Person 2 and source IDs with Person 3 before changing
them. Follow the specification's shared schema change protocol.

## Files and usage

- `data/synthetic/role_catalog/roles.json`: three roles with stable IDs, sector,
  task IDs, source IDs, update date and a synthetic flag.
- `data/synthetic/role_catalog/role_skills.json`: role/skill pairs with importance
  weights, evidence references and a synthetic flag.
- `data/synthetic/role_catalog/taxonomy.json`: skill labels and aliases, tasks,
  sectors and taxonomy version.
- `data/synthetic/role_catalog/sources.json`: synthetic source inventory. The
  source URL is null because these records were authored for this fixture.
- `data/demo/roles_response.json`: complete example response, generated by the
  loader and checked against it in tests.
- `src/schemas/role.py`: Pydantic contract and reference validation.

Run from the repository root with Python 3.10 or newer:

```bash
python -m pip install -r requirements.txt
python -m src.ingestion.catalog
python -m unittest discover -s tests -v
```

Python consumers can use the typed contract:

```python
from src.ingestion.catalog import load_role_catalog

catalog = load_role_catalog()
requirements = [
    row for row in catalog.role_skills if row.role_id == "role:data_analyst"
]
```

`get_roles()` returns a JSON-compatible dictionary of the complete `RoleCatalog`.
Its keys are `schema_version`, `synthetic`, `taxonomy`, `sources`, `roles` and
`role_skills`. Dates serialize as ISO date strings; the response is an object,
not a bare role list. No network requests or database are needed.

Person 5 can attach this adapter to the future FastAPI app:

```python
from src.ingestion.catalog import get_roles
from src.schemas.role import RoleCatalog

@app.get("/api/roles", response_model=RoleCatalog)
def roles():
    return get_roles()
```

This snippet assumes Person 5 has created `app`; this handoff does not start an
HTTP server or change the starter application's entry point.

## Consumer expectations

| Consumer | Use |
|---|---|
| Person 2 | Normalize aliases to canonical skill IDs; join `role_skills` by role ID for matching and gaps. |
| Person 3 | Join role task IDs to taxonomy tasks for outlooks and scenarios; synthetic sources cannot support factual trend claims. |
| Person 4 | Join skill and role IDs for course coverage and SDG mappings; retain Person 2's actual gaps. |
| Person 5 | Display role titles and sector labels; retain a visible synthetic label; use the response snapshot before wiring the loader. |

Importance is an illustrative weight in `[0, 1]`, not a probability, measured
frequency, proficiency level or fit score. Weights need not sum to one. A missing
role/skill pair means there is no requirement in this fixture. `evidence_ids`
currently reference source inventory IDs; this is not a separate evidence table.

For a predictable matching example, a profile containing `skill:python` and
`skill:sql` matches those two Data Analyst requirements and lacks statistics,
data visualization and communication. IT Support Specialist has no requirements
matching those two skills. Person 2 owns the scoring formula; this fixture does
not prescribe scores or rankings.

## Replacing the mock

The loader is explicitly for synthetic fixtures and sets `synthetic=true`.
Production ingestion should construct the same `RoleCatalog` contract with the
appropriate provenance flags, reviewed sources and dates, then pass it to the
same consumers. Preserve canonical IDs when replacing sample requirements.
Do not place these synthetic files in `data/processed` as observed data.

Validation rejects duplicate IDs or role/skill pairs, dangling references,
out-of-range weights, unlabeled records within a synthetic catalog, and roles
without requirements. Schema or taxonomy changes require updated fixtures,
response snapshot and consumer coordination.

## Person 3 Data Analyst example — initial contract proposal

Copy-ready integration notes for Persons 4 and 5 are in
[the Role 3 handoff](ROLE_3_HANDOFF.md).

See [Role 3 Data Analyst example](ROLE_3_DATA_ANALYST.md) for provenance,
priority rules, limitations and commands. Existing Person 1 IDs are unchanged.

`src.intelligence.outlook.get_outlook(role_id, scenario_id="baseline")` returns
a typed `RoleOutlook` with cited contextual task interpretations and a nested
`ScenarioResult`. `get_outlook_response` returns a JSON-compatible dictionary.
`data/demo/data_analyst_outlooks.json` provides baseline, `moderate_ai_change`,
and `rapid_ai_change` responses for integration. Person 4 should review the
additive priority adjustment contract before wiring it into planning.

Role 3 also provides `src.intelligence.feeds.refresh_evidence()` and
`get_refresh_status()` for an explicit, bounded reviewed-source refresh and its
cached/unavailable warnings. See [the refresh guide](ROLE_3_EVIDENCE_REFRESH.md).
Outlook requests remain offline and use the last validated ledger. Person 5
should display refresh status alongside source publication dates, not treat a
recent fetch as evidence of a recent publication.

The separate `src.intelligence.impacts.get_evidence_chain_response(role_id)`
adapter exposes source-to-finding-to-task-to-skill reasoning. See
[the evidence-chain guide](ROLE_3_EVIDENCE_CHAIN.md) for its example and display
requirements. These proposed qualitative implications do not change fit scores
or numerical scenario priorities. The internal evidence ledger now accepts
0.2.0 chains and legacy 0.1.0 inputs; the role catalog and existing outlook
response contracts retain their versions.

Automatic candidate extraction is a separate command:
`python -m src.intelligence.extraction --url APPROVED_URL`. It uses Gemini and
writes `ExtractionRecord` objects under `data/review/candidates/`, with
`review_status=pending_review`. These are not `ReviewedSource`, `RoleOutlook` or
accepted evidence. See [the extraction guide](ROLE_3_EXTRACTION.md).

The [approval command](ROLE_3_APPROVAL.md) prepares a typed `ApprovalPlan` and
admits it only with an explicit reviewer and `--approve`. `ReviewedSource` now
accepts an optional `FindingApproval` provenance record and may contain zero task
interpretations for finding-only admission. Approval provenance is stored in the
review definition and refresh snapshot. The existing `TrendSignal`, `RoleOutlook`
and scenario contracts are unchanged. Unmapped accepted findings are not shown in
role-specific outlooks. Mapped findings preserve their evidence-type qualifier
and reviewed limitations in the displayed claim.

`src.intelligence.proposals.generate_task_skill_proposal()` now generates a
separate `TaskSkillProposalRecord` from an admitted approval definition and role
catalog. See [the task/skill proposal guide](ROLE_3_TASK_SKILL_PROPOSALS.md).
Records remain `pending_review` under `data/review/task_skill_proposals/`; they
do not alter `RoleOutlook`, `ScenarioResult`, fit or weights. Task/skill scope is
validated against existing catalog links. `load_current_proposal()` checks
accepted-input, catalog and prompt-version fingerprints before review.

## Person 4 learning planner contract

Person 4 has made an internal Python module, not an HTTP service. See
[the Person 4 handoff](PERSON_4_HANDOFF.md) for schemas, selection behavior,
validation rules and integration notes.

### Direct-call usage

```python
from src.reskilling.planner import build_learning_plan

result = build_learning_plan(
    profile,
    selected_role_match,
    scenario_id,
    country="Malaysia",
    preferred_language="English",
    search_provider=course_search_provider,
)
```

### Inputs and output

Inputs are a reviewed `SkillsProfile`, the selected `RoleMatch`, one of
`baseline`, `moderate_ai_change` or `rapid_ai_change`, country, preferred
language and an optional replaceable `CourseSearchProvider`.

The return value is a `PlanningResult` containing:

- `plan: LearningPlan`
- `validation_logs: list[CourseValidationLog]`

### Priority contract

- Actual gaps come only from `RoleMatch.missing_skills`; scenario priorities do
  not establish proficiency or create gaps.
- The planner joins gaps to `get_outlook(role_id, scenario_id)` priorities by
  `skill_id` and consumes `adjusted_priority` directly.
- Do not multiply the baseline by the adjusted priority or apply the adjustment
  twice.
- The plan preserves `baseline_priority`, `applied_adjustment`, the user's
  reviewed skills and the selected role's fit score.

### Course discovery and validation contract

- Discovery searches trusted providers first and uses wider-web fallback when
  trusted results are insufficient.
- Each validation batch is bounded to at most 20 candidate courses.
- Only successfully verified course records can be recommended. Invalid,
  nonexistent or unverifiable records are withheld and logged.
- An unknown price is not treated as free.
- Without a `CourseSearchProvider`, planning uses only the verified local cache.

### Current limitations

- The current catalog contains no pre-approved courses, so a search provider or
  previously verified cache entries are required for recommendations.
- Generic HTML validation may withhold legitimate JavaScript-only course pages.
- The current non-baseline scenario fixture supports Data Analyst only.
- Budget and time are returned as course metadata and selection tie-breakers;
  user filtering remains a frontend concern.
- The module does not start an HTTP server.
