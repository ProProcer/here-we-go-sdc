# Person 5: CV-first web application

The local application connects the real O*NET 0.2 backend to CV upload, explicit
skill review, ranked matches, role detail, supported scenarios, learning
objectives and SDG explanations. No public deployment is claimed.

## File ownership

```text

src/api/routes.py               Versioned HTTP adapters and request contracts
```

The frontend uses React, Vite, Tailwind CSS and strict TypeScript. `frontend/dist/`
is generated by the production build and ignored in Git. There are no temporary
helper scripts or extra production services. The former Jinja template and
imperative browser script have been replaced.

## Frontend design system

Explore Role opens a full role overview page. Its AI outlook button opens the
next page, with compact research cards and evidence available in disclosures.
AI outlook lists only articles assessed as `connected` ("Career connection shown")
and their associated interpretations. Other assessment outcomes and the general
research catalog are omitted. Role pages show the full occupation description
directly and keep matching skills and skills to explore in fixed-height scrollable
panels. Navigation uses a back button and the AI outlook action below the role
details. Assessment and source-health help sit below the roadmap action with
plain question-mark controls; other disclosures and source actions use buttons.

The learning roadmap is a dependency graph inspired by the category-and-arrow
layout of NeetCode. Short (1–3 month), standard (6 month), and long (12 month)
choices curate a focused set of practical modules within the chosen weekly study
budget. Basic skills are embedded in role-specific work instead of separate stops.
The AI uses the shared model client and supplied tasks, gaps, known skill levels
and selected verified course records. A structural draft is locally normalized
and validated: only supplied IDs are accepted, dependencies must be acyclic,
listed course prerequisites are retained, course durations count once, and the
combined course/practice time must fit the budget. One repair attempt shares the
45-second request budget. Course coverage remains distinct from skills practised
implicitly in a project. Per-course chips use that course's actual skill IDs.
No raw CV text, evidence passages, session IDs or profile identifiers reach this
AI task. Validated results are cached in memory; failed responses are not cached.
If AI is unavailable or unconfigured, an explicitly labelled application outline
is shown. Module details expose deliverables, grouped skills, verified courses,
optional external sources and dependency reasons. JSON export includes the curated
graph alongside the full underlying resource plan.
Weekly pace and learning scenario use the shared styled, keyboard-accessible
selection control. Scenario planning follows the roadmap in the page flow.
The roadmap's SDG action opens a separate page with a return button; its study
pace remains selected when navigating between those pages.
AI news shows an animated circle during the initial fetch, source refresh and
queued/running career assessment. Completed empty results and failures stop it.
Roadmap steps also offer compact links to real courses and provider catalogs
matched by topic, including HP LIFE, Saylor University, Coursera, edX, Khan
Academy, Microsoft Learn and IBM SkillsBuild. These optional choices are separate
from the planner's verified course records and do not inherit their cost or time.
Both pages keep Explore careers active in the sidebar. Back buttons and browser
history navigate between pages; editing skills clears dependent role and plan
data. Refresh starts a new in-memory session at Upload CV.

The journey screens share white surfaces, a soft `#F5F8FC` canvas, primary
blue `#1689F9`, rounded cards and pill buttons. Darker blue is used on small
white-text controls for contrast. Core palette, radius, content-width and shadow
tokens live at the beginning of `frontend/src/styles.css`, with Tailwind theme
aliases for utilities. Component styles remain centralized to preserve the
existing visual design. Inter is served locally
from `frontend/public/fonts/` with its SIL Open Font License; no font service receives
visitor requests.

React components provide reusable icons, chips, empty states, career cards,
skill rows, evidence disclosures, roadmap steps and SDG connections. React owns
the rendered state instead of rebuilding large HTML strings. The desktop
sidebar can collapse into an icon rail and becomes a compact bottom navigation
on mobile. Green outlines and connectors track prepared stage outputs:
profile loaded, review submitted, role explored and roadmap generated. Editing
skills or preferences clears dependent progress. The roadmap marker means the
plan is ready, not that the user has completed its learning activities.
The sidebar animates its width, labels and logo position while respecting reduced
motion. The collapsed rail keeps the noninteractive logo at the bottom; the demo
label is removed. The header has
no step counter. Roadmap limitations use short notes and cost/time facts; full
backend warnings remain in a nested Technical details disclosure and JSON export.
The role overview and AI outlook use full pages, with heading focus on navigation
and expandable details for longer explanations.

- Upload: one drop area, a continuously rotating spinner, randomized playful
  messages in a transform-only reel, and expandable privacy/help. Changing
  messages are hidden from screen readers; a stable status is announced instead.
  The spinner and text reel animate automatically with no motion button. At the
  user's request, these two loading indicators remain animated even when system
  motion reduction is enabled; other UI motion still respects that preference.
  The first upward slide begins promptly, even on shorter uploads.
  Successful uploads automatically open skill review. Returning to Upload shows
  the filename, success confirmation and an option to upload another CV. Filenames
  stay in browser memory only and update after successful parsing; a failed
  replacement leaves the previous profile and filename intact.
- Review: separate general/tool skill groups, explicit confirmation, removal and
  restore controls; CV evidence and self-reported level stay expandable. Added
  and removed state is local presentation metadata, never a new scoring input.
  Page 2 is sequential: review skills first, then choose an optional career goal
  and learning preferences. Back navigation preserves selections. A progress
  ring fills with confirmed active skills, with its caption below the circle.
  A real select-all checkbox supports checked, unchecked and partial states;
  removed skills are excluded. Choosing no goal is an explicit continue option.
  CV evidence uses a native disclosure with an SVG chevron and a spaced evidence
  panel. Skill/occupation search uses a neutral autocomplete with combobox/listbox
  semantics, arrow-key navigation, Enter selection, Escape dismissal and a clear
  action. Keyboard focus remains visible without the former blue input highlight.
  Self-reported levels and occupational-family filters share a custom Select
  component with selected checkmarks, arrow/Home/End navigation, type-ahead,
  Enter selection, Escape/outside dismissal and upward opening near the viewport
  edge. Help disclosures use circled question marks; other disclosures use SVG
  chevrons rather than text symbols.
- Explore: one featured match, supporting career cards and a persistent chosen
  target outside the filters. An empty confirmed profile shows no scored roles.
- Roadmap: the first five steps are visible, with later steps and each step's
  full objective, practice, resources and SDGs available on expansion. Scenario
  controls show only supported choices as enabled, with actual priority deltas.

Backend scoring, identifiers, evidence admission, resource verification and
session/privacy contracts are unchanged. Missing evidence and missing verified
courses have explicit empty states. The full backend learning goal is preserved
in expanded step details and the JSON export even when its preview is shorter.

After pulling `34f20ed`, the real ledger contains one Google Research source and
two contextual BI task interpretations. These flow through the existing outlook
route into the AI outlook page. `CareerBackend.skill_evidence()` and `role_impacts()` now
have read-only HTTP routes and expandable UI panels with citations, conditions,
review coverage and limitations. Their committed approval stores remain empty;
pending proposals are never presented as approved evidence. Optional evidence
lookup failures do not prevent viewing a career or building its roadmap.
The existing `learning_priority_evidence` metadata is displayed in the roadmap,
separating reviewed research adjustments from hypothetical scenario adjustments.
The assessment store is empty. The course cache remains empty; its existing
store is shared explicitly by the app, planner and course-status endpoint.
No new discovery provider, AI job, approval action or scoring policy was added.
The public CV/matching/planning journey makes no Gemini calls.

Gemini setup is needed only to run the existing Role 3 background review jobs.
For scheduled runs, configure `GEMINI_API_KEY` in GitHub repository Actions Secrets.
For jobs explicitly run on Replit, use Replit Secrets. Merely setting a key does
not run these jobs or approve their proposals. Never put a key in a `VITE_`
variable, browser storage, committed files or an end-user upload form.

## Run and configuration

Install `requirements.txt` and use Node.js 22.12+ to build the frontend, then run:

```bash
npm --prefix frontend ci
npm --prefix frontend run build
python -m src.main
```

Open `http://localhost:8000`. For live frontend development, keep Python running
and run `npm --prefix frontend run dev` in a second terminal. Open port 5173;
Vite proxies `/api` to port 8000. Production uses the built frontend on port 8000,
so frontend changes there require a rebuild. Interactive route documentation is at `/docs`.
The application loads one `CareerBackend` at startup, reusing its catalog and
matcher. The deployment entry point is `python -m src.main`: it binds to
`0.0.0.0`, reads `PORT` (default 8000), and explicitly uses a single Uvicorn
worker even when the hosting environment sets `WEB_CONCURRENCY`.

Replit configuration is in `.replit` and `replit.nix`. It selects Python 3.12
and Node.js 22, installs locked npm dependencies (including build tools), builds
React, installs web dependencies into a Linux `.venv`, and maps internal port 8000 to
external port 80. Production builds install dependencies before startup; the
production run command only starts the application. The development Run button
also handles first-time dependency setup. Replit's native runtime configuration
adds C++ and zlib libraries for CPU OCR and PDF wheels. The optional RunPod
SDK now has its own `runpod/requirements.txt` and is not installed by the web app.
See README's **Deploy on Replit** steps, including the single-server Reserved VM
selection. No public deployment or account usage is represented by these files.
FastAPI serves both `/api/v2` and the Vite output from the same origin. Node is
only required for the build; there is no separate production Vite server or
CORS configuration. If a build is missing, `/` explains how to build it with a
503 response while the Python API remains available.

Use one application worker and instance. Profiles are in memory, with a one-hour
absolute expiry, at most 256 sessions, and no persistence across restarts. Expired
records are removed on access or subsequent session creation; all are cleared at
shutdown. Session tokens live in browser memory and are sent through
`X-Session-ID`, never URLs. Reloading the page starts a new browser journey;
the prior server session expires automatically. Uploading a replacement CV in
the same journey deletes the previous active session.

## CV intake

The upload is a raw file body with `X-Filename`, bounded to 2 MiB while streaming
before decoding. There is no multipart spool, upload folder or retained source CV.
The worker receives bytes over stdin and returns bounded text as JSON.

- PDF: existing pypdf validation, maximum five pages, text extraction; blank-text
  pages are rendered using pypdfium2 and read with RapidOCR.
- DOCX: bounded ZIP expansion (10 MiB, 1,000 entries), paragraph/table/header/footer
  text. Embedded scans inside DOCX are not OCRed; export those to PDF/images.
- TXT: UTF-8 or UTF-8 with BOM.
- JPG/PNG: local CPU OCR, including orientation metadata handling, maximum eight
  megapixels. PDF OCR rendering is bounded to the same pixel limit per page.

Decoding runs in a child process with a 60-second timeout. At most two extraction
workers can run concurrently per application worker. These bounds are not a full
process memory sandbox; production hosting should additionally constrain memory
and request rates. OCR uses the models packaged with RapidOCR; no inference API
or GPU is used. OCR accuracy, language coverage and reading order vary. DOCX and
PDF text may not preserve complex visual order. Users can correct skills or use
the manual fallback.

The sample is a real, one-page PDF rendered from `graduate.txt`. Both **Try
sample** and an uploaded/downloaded copy call `backend.extract_profile`; neither
injects a skill profile or matching result. All extracted claims start unverified.

## HTTP contract

All routes below use `/api/v2`.

| Method and route | Contract |
|---|---|
| `GET /samples/graduate.pdf` | Download the fictional CV PDF |
| `POST /profiles/upload` | Raw bytes and `X-Filename`; returns session token, revision and extracted profile |
| `POST /profiles/sample` | Parse the sample PDF through the same intake pipeline |
| `POST /profiles/manual` | Empty session for manual correction/fallback |
| `PATCH /profiles/current` | Token header; revision, confirmed skill list, optional target/interests/constraints |
| `DELETE /profiles/current` | Token header; discard session |
| `GET /skills?q=...` | Up to 25 canonical skill/alias search results |
| `GET /roles?q=...&offset=0&limit=25` | Paged real-catalog role adapter; limit at most 100 |
| `GET /roles/{role_id}` | Real occupation detail and provenance |
| `GET /matches?revision=...&top_n=10` | Token header; reviewed profile required; top-N plus original-rank target pinning |
| `GET /roles/{role_id}/outlook?scenario_id=baseline` | Catalog-aware outlook and available scenarios |
| `GET /roles/{role_id}/evidence` | Catalog-aware reviewed evidence chains |
| `GET /roles/{role_id}/skill-evidence` | Existing approved shared skill interpretations, canonical labels and coverage counts |
| `GET /roles/{role_id}/impacts` | Existing approved conditional role/task impacts and shortlist coverage |
| `GET /evidence/status` | Real-catalog refresh status, separate from legacy fixtures |
| `GET /courses/status` | Existing verified-cache count, catalog timestamp and empty/available state |
| `POST /pathways` | Token header; revision, role, scenario and optional selected software IDs |

The review PATCH accepts only explicitly confirmed retained skills, canonical
labels and valid role IDs. Unchecked extracted claims are omitted from the
reviewed profile. Profile edits invalidate displayed matches/plans. Stale
revisions return 409; missing/expired sessions return 401; unknown roles return
404; oversized uploads return 413; invalid document/selection requests return
422. Validation responses omit submitted values and CV evidence.
Unreadable optional evidence or course catalogs return a sanitized 503. All of
the new GET routes are read-only and invoke no external AI or approval workflow.

The planner recomputes the selected role match from the server profile. Client
scores and gap lists are never accepted. Budget applies through profile
constraints; weekly hours derive an estimated number of weeks only when verified
course hours exist. Software choices remain optional and separate from general
gaps. Scenario changes recompute priorities/plans and retain personal fit.

## Provenance and present limitations

Use real 0.2 role IDs and occupational families. The legacy mock 0.1 adapters and
their citations remain separate; their data are never substituted into real-role
responses. Render O*NET attribution, publication/retrieval dates, source coverage,
team interpretations, limitations and hypothetical assumptions.

The real ledger and verified course cache currently contain no accepted sources
or courses. Outlooks therefore show insufficient evidence; plans return actual
prioritized gaps, practice activities and SDG 4.4 connections with
`verified_resource_not_found`. This is functional integration, not completion of
source-backed course recommendations. Persons 3 and 4 still need to admit real-role
evidence and populate the verified resource cache or connect a search provider.

Only Business Intelligence Analysts currently supports the moderate/rapid
hypothetical scenarios. The selector reads `available_scenarios`; all other
occupations expose baseline. Refresh/extraction/approval remain owner-run
workflows, outside the public UI. Pending AI-generated proposals never become
published evidence or numeric priorities automatically.

## Added tools

FastAPI, Uvicorn and Starlette provide HTTP serving. React renders the interface;
Vite builds it, TypeScript checks the frontend contracts and Tailwind supplies
compiled utilities alongside centralized component styles. npm dependencies
and exact resolutions are in `frontend/package.json` and `package-lock.json`.
python-docx reads DOCX; Pillow handles images; pypdfium2 renders scanned pages;
RapidOCR and ONNX Runtime perform local CPU OCR. Version pins are in
`requirements.txt`. HTTPX and Playwright are development-only dependencies in
`requirements-dev.txt`. Third-party distributions and OCR models retain their
own licenses; retain their notices in deployed distributions and include these
tools/models in the team's declaration.

## Cached maps and language selection

`resultCache.ts` keeps learning maps and AI outlook responses in browser memory,
with session/settings/language keys and shared in-flight requests. Returning from
SDG or role details reuses the completed result. Profile edits clear the browser
cache. Server learning proposals persist for seven days in
`.trend-cache/learning-maps.json` and are revalidated before reuse; this file stores
generated modules and hashed keys, never raw CV passages or the input profile.
The existing live-trend cache continues to retain dated research assessments.

The top-bar language picker supports English, Bahasa Melayu and Simplified Chinese
for Mandarin readers. `i18n.ts` reads the bilingual interface catalogue in
`locales.json`; only the language preference is written to browser storage.
Switching language updates labels and accessibility text without resetting the
journey. Public roadmap prose and outlook interpretations use the shared AI
translation service with a separate seven-day cache. Source titles, quotations,
provider facts, IDs and graph relationships remain canonical. A failed translation
shows original English content with an explicit notice rather than hiding results.
